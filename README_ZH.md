## 它解决什么问题

出口企业同时面对欧盟 PPWR、电池法、CBAM、EUDR、REACH / RoHS 等多部法规，常见四类问题：**同一事实反复重填、结论被写死成属性、法条藏在提示词里、答案给不出依据**。

kernelPlia 要回答的是：**某项制度在某时点、对某主体、就某对象要求什么，依据是哪一条。** 用大白话提问，它给出结论，并把每条结论钉回具体的条、款、项。点开引用能看到官方公报原文页，被引的几行有高亮框。

第一个语料是欧盟包装法规（PPWR，Regulation (EU) 2025/40）。

## 工作原理

```
提问 ──► 条款号精确定位 ──► 主题词召回 ──► 一跳链接扩展 ──► 冲突判定
                                                              │
                                            ┌─────────────────┴──────────┐
                                          命中                          未命中
                                            │                            │
                                     暴露并阻断                    上下文装配
                                   （不调模型）                  （10K/15K 闸门）
                                                                         │
                                                             结构化输出 + 六条服务端校验
                                                                         │
                                                              条款级引用 · 位阶分级 · 原文页高亮
```

检索以结构化条文索引为主，向量检索兜底，三条通路最后都回落到同一套条款锚点。**适用性、位阶冲突、生效时点由规则计算，不由相似度决定。**

## 三个不太常见的设计

| 设计 | 一句话 | 为什么 |
|---|---|---|
| **无引用即不输出** | `citations` 是 schema 必填字段，外加六条服务端校验 | 用 schema 保证，不靠提示词 |
| **冲突暴露并阻断** | 官方文件互相矛盾时不出答案，先把两份来源和位阶摆出来 | 不替用户悄悄选一个 |
| **触发与召回解耦** | 阻断只看触发条款自己的分数，不用 idf | 阻断是红线，不能随索引规模变化 |

<details>
<summary><b>一、「无引用即不输出」由 schema 保证，不靠提示词</b></summary>

答案对象里 `citations` 是**必填字段**，由结构化输出（`json_schema` + strict）在生成阶段强制。
这和「JSON 模式」不是一回事：后者只保证输出是合法 JSON，不保证字段、必填、枚举符合约定。

模型仍可能编造条款号，所以后面还有六条服务端校验，每一条对应一条具体的红线：

| | 校验 |
|---|---|
| 1 | 知识模式无引用 → **不输出**，走兜底文案 |
| 2 | 引用的条款号必须**在库中存在且已具名采纳**，编造的直接丢弃；全部编造则不输出 |
| 3 | 引用按**效力位阶升序**重排，位阶以库为准，模型把 FAQ 标成位阶 1 也不算数 |
| 4 | 位阶 3、4 由服务端补上「委员会解释、无法律约束力」标注 |
| 5 | 声称「官方文件未覆盖」却没给推理说明 → 不输出 |
| 6 | 命中已知冲突 → 不出答案正文 |

**宁可不答，不可无据而答。**

</details>

<details>
<summary><b>二、冲突暴露并阻断，不自动择一</b></summary>

官方文件之间会打架。比如一份授权决定豁免了某类包装的重复使用义务，而三个月后发布的
官方实施指南三节都没提这个豁免。

多数系统会挑一个答案给你。这个内核**不出答案正文**：先把两份来源、各自的效力位阶、
以及位阶指向哪一边摆出来，用户确认知悉后才继续。确认之后仍按位阶作答，
**不提供「按另一份作答」的选项**。

阻断这一轮**不调模型**，成本接近零。

</details>

<details>
<summary><b>三、触发与召回解耦</b></summary>

阻断与否，只看**触发条款自身**对这句提问的「自足分数」，
完全不看它有没有进召回集：

```
阻断 ⟺ max(自足分数 over trigger_clause_ids) ≥ 阈值
        ∧（语境词为空 ∨ 提问命中其中任一）
```

分数是 `max(len(词) ** 1.2 × 字段权重)`，**没有 idf**。

为什么不用 idf：如果接在 top-N 或文档频率上，索引一变大、召回竞争一激烈，
同一句提问就会时而阻断时而不阻断。而阻断是红线级的确定性要求，
**不能随索引规模漂移**。压制高频噪声改用一份人工维护、具名采纳、改动须回归的
停用词表（`demo_index/stopwords.yaml`），它的值只在有人改那份文件时才变。

</details>

<details>
<summary><b>踩过的坑：分词、裁剪顺序、基线</b></summary>

**分词。** 中文原来按 2–6 字滑动 n-gram 切。问「我的包装重金属超标了会怎样？」
会切出 `包装重`。它在提问里跨「包装|重金属」的词界，在另一条讲重复使用的条款标题里
跨「包装|重复」的词界，**两边都不是中文里的词**，字面却一致，于是把那条毫不相干的条款
顶过了冲突闸门；随后冲突关联条款的最高保留优先级，又把召回排第一的限值条款挤出了上下文。
**问重金属，答重复使用。** 现在改成先用 jieba 分词、再在词序列上滑窗，相邻才拼、遇虚词断开。

**裁剪顺序。** 超预算时按「丢了会不会答错」排序丢弃，而不是按「是不是扩展进来的」。
光有档位不够，它区分不了「派生与来源同时在场」和「来源已经被丢掉」两种情况。
所以补了两条：派生的排序键**挂在来源键之后**（同档时来源必然在前）；
一条位阶 3/4 的解释与它上扩出来的位阶 1/2 法条，是**裁剪意义上不可分割的一个单元**。
只改排序，切口落在两者之间时会留下一条没有法条依据的解释；只做绑定，倒挂本身又没修。

**基线不许吸收完整失败。** 「已知的可接受损失」这类基线表有个陷阱：
一条用例把期望引用丢光了也能记进去，测试全绿，而这条用例其实已经完全失效。
所以另设一条不看基线、直接报错的上限：**单条用例不得丢失其全部期望引用**。

</details>

## 我的角色与产品决策

我是这个项目的产品 owner，负责完整产品形态的设计和所有产品裁决，并把 V0 推到上线。几个具体决策：

- **定义红线**：设计规范迭代到 v1.9，沉淀 23 项决策、15 条红线。「无引用即不输出」「冲突时阻断」都来自这里。
- **发现指标陷阱**：某个模型配置首字节 1.4 s 达标，但总耗时 245 s。据此把验收改成「首字节 + 总耗时」双指标，对比 4 种配置后选定 lite 并关闭深度思考。
- **召回调优改机制，不调阈值**：54 组参数扫描证明剩余缺口是结构性的，于是改机制（链接双向扩展、语料自名词停用），而不是继续调阈值。
- **手测发现分词 bug**：「问重金属、答成可重复使用」就是亲手测出来的，见上文「踩过的坑」。
- **坚持真实问答**：否决了「预置问题演示」方案。首屏图谱只点亮 1/3，节点在回答中被引用后才解锁名字。
- **北极星指标**：每份交付件消耗的专家分钟数。

<details>
<summary><b>完整产品形态与路线图（V0 已上线，V1 / V2 未开发）</b></summary>

**两层六模块**

| 层 | 模块 |
|---|---|
| 知识层 | K1 语料与权利登记 · K2 结构索引与规范断言 · K3 检索与问答 |
| 判定出证层 | J1 适用性判定 · J2 缺口与取数 · J3 出件与台账 |

与企业事实底座只通过事实快照单向对接：**事实共享、结论隔离**。

- **时态模型**：浮动生效日建模为可求解表达式；周期性义务（如 EPR 两层申报截止）单独建模；规范断言双时态，只存计算轨迹、不缓存结论。
- **缺口求差**：按满足、缺失、未知、冲突、不可得、权利阻断 6 种状态求差；取数请求引用 PPWR 第 16(1) 条作为法律抓手。
- **交付件**：同一套判定投影为技术文档与 DoC、EPR 申报量表、平台问卷、客户问卷 4 类交付件。

**版本阶梯**：V0 条款级问答 → V1 义务日历 + 报价器 → V2 技术文档与 DoC 出件 → 多制度内核。

</details>

## 快速开始

```bash
docker compose up -d                      # PostgreSQL 16
pip install -r requirements.txt
python scripts/init_db.py
python -m ingest.load                     # 装载 demo_index/
pytest -q                                 # 34 项，不需要模型
uvicorn app.api:app --reload              # http://127.0.0.1:8000
```

问答需要一个模型。在 `.env` 里填 `ARK_API_KEY`（火山方舟，OpenAI 兼容接口），
或改 `app/providers.py` 换成别的模型。**换模型前先确认它支持等价的严格结构化输出**，
不能只是「JSON 模式」，否则第一条红线就从 schema 保证退化成了重试与丢弃。

<details>
<summary><b>诊断工具：为什么召回了这些条款</b></summary>

```bash
python scripts/why.py "包装里重金属最多能有多少？"
```

它会打印候选词、每条召回的来源、三条冲突各自的自足分数以及是**哪个词**贡献的，
还有上下文按什么次序保留和丢弃。两次归因错误都是靠它纠正的。

</details>

<details>
<summary><b>首屏图谱</b></summary>

前端首屏的动态图谱**画的是真实的条款关系**：节点是已采纳的条款单元，边是登记的
`derogates` / `explains` 关系，沿边跑的脉冲就是一跳扩展的样子。默认只显示位阶与拓扑、
不显示条款号；**一个节点在本会话的回答里作为引用出现过之后，才获得名字、才可点开**。

</details>

## 这个仓库里没有什么

**索引。** 仓库里只有 10 条条款单元的演示切片（`demo_index/`），足够把上面每条机制跑出来。
完整索引、工作译本、内部答题纪律、完整用例集以及「什么叫答对」的口径都不在这里。

这是有意的取舍：**公开的是机制与纪律，真正花工夫的内容判断不公开。** 两者可以切开，
所以机制可以公开。

**明确不做**：自动择一化解冲突、无引用的「常识性」回答、法律意见。
